第1章 インターネットとネットワークの仕組み(12問)
==================================================

Q1. インターネットとは
「インターネット」と「Webブラウザで見るホームページ」は同じではありません。
ホームページはインターネットを使って提供されるサービスの一つ。
インターネットは世界中のコンピューターをつなぐネットワークそのもの。（通信インフラ）

Q2. IPアドレスとポート番号
localhost は自分自身のコンピュータを指す特別なホスト名。
ポート番号はコンピュータの中の宛先。
8080はSpring Boot、5173はViteというように、通信を正しいプログラムに振り分けるために必要

Q3. DNS
DNSはドメイン名をIPアドレスに変換する電話帳のような役割を果たしている

Q4. HTTPとは
HTTPは HyperText Transfer Protocol の略
HTTPはブラウザ(クライアント)とサーバーが「こういう形式でリクエストを送り、こういう形式でレスポンスを返す」
という取り決めを定めたプロトコルで、Webにおけるデータのやり取りの基盤。


Q5. HTTPとHTTPSの違い
HTTPは通信内容が暗号化されない平文通信、HTTPSはTLS/SSLという仕組みで通信内容を暗号化するプロトコル。
HTTPだと通信経路上で第三者に内容を盗聴・改ざんされる危険があるため、現在のWebサイトはHTTPSが主流になっている。

Q6. リクエストとレスポンス
飲食店の注文で例えると、
お客様(クライアント=ブラウザ)が店員(サーバー)に「これをください」と注文する行為が「リクエスト」、
それに対して店員が料理を運んでくる行為が「レスポンス」。

Q7. HTTPメソッド
GET: 情報を取得する。ニュースを見る
POST: 新しく作る。注文する
PUT: 全体を置き換える。注文内容を全て変更する。
PATCH: 一部だけ変更する。一品だけ変更する
DELETE: 取り消す・消す・注文をキャンセルする。

Q8. HTTPステータスコード
- 200　正常に成功
- 201　新しいリソースの作成に成功
- 400　クライアント側のリクエスト内容に誤りがある
- 404　指定されたリソースが存在しない
- 500　サーバー側でのエラー


Q9. JSONとは
JSONはデータを {"key": "value"} の形で表現するテキストベースのデータ形式。
フロントエンド(TypeScript)とバックエンド(Java)のように異なる言語間でも
共通のデータ形式としてやり取りしやすいため、広く使われてる。

Q10. APIとは
APIとはプログラム同士が機能やデータをやり取りするための窓口・取り決め。
直接データベースにアクセスしない理由は、以下の3つ。
①データベースの接続情報やSQLをブラウザ(誰でも見える場所)に晒さないため(セキュリティ面)。
②入力チェックやビジネスロジックをバックエンド側で一元管理するため。
③データベースの構造が変わってもAPIの形が変わらなければフロントエンドを直さずに済むため。

Q11. CORSとは
CORSはあるオリジンで動くWebページから、別のオリジンへのアクセスを許可するかどうかをサーバー側が制御する仕組み。
ブラウザは標準では異なるオリジンへのリクエストを安全のためブロックする(同一オリジンポリシー)ため、
明示的に許可設定しないと、フロントエンドからのAPI呼び出しが失敗するためCORSが必要。

Q12. クライアントとサーバー
- ブラウザ　→ クライアント
- バックエンド　→ サーバー
- データベース　→ サーバー

第2章 Webアプリケーションの構造(8問)
==================================================

Q13. フロントエンドとバックエンド
フロントエンドは見た目・操作を担当する部分
バックエンドは画面には表れないデータ処理・保存・業務ロジックを担当する部分
このアプリでは、Reactがフロンドエンド
Spring Bootがバックエンド

Q14. 3層構造
1つのプログラムに全部詰め込むと、変更の影響範囲が予測できず、保守が困難になるため。

Q15. データの流れ
ユーザーがボード上の「+カードを追加」を押しフォームに入力して送信ボタンを押す
→ Reactがリクエストを送信
→ Spring Bootがリクエストを受け取り、
→ PostgreSQLのtasksテーブルに収納
→ 保存されたタスク(IDや作成日時付き)がレスポンスとして返る
→ Reactがそのレスポンスを受け取り、画面を更新
→ Reactが再描画され、新しいカードがボードに表示される。

Q16. エンドポイントとURL設計
考え方は、URLを「操作名」ではなく「対象となるリソース」で表現している。
今回の場合、 tasks が「タスク」というリソースを表している。
{id} は、タスクを識別するためのIDが入る場所。実際にはIDの値が入る。


Q17. 同期処理と非同期処理
同期処理は、「注文した料理が完成するまで、その場で待ち続ける」イメージ。
一方、非同期処理は、「料理を注文したあと、完成を待っている間に別のことをする」イメージ。
同期処理だと画面操作がフリーズしてしまうため、非同期処理が必要

Q18. SPA(シングルページアプリケーション)
Webサイトは、リンクをクリックするたびにサーバーから新しいHTMLページ全体を取得し直して画面を再読み込みする。
SPAは最初に1枚のHTMLを読み込んだ後は、必要なデータだけをAPI経由で取得し、JavaScript(React)が
画面の一部だけを書き換えます。本プロジェクトもボード画面はページ遷移せず、カードの追加・編集・削除・移動はすべて
画面全体のリロードなしに反映される。

Q19. 入力チェック(バリデーション)の多重防御
フロントエンドのチェックはユーザー体験の向上(即座にエラーを表示できる)のためのものですが、
ブラウザの開発者ツールなどで簡単に操作できてしまいます。
バックエンド側でも同じチェックを行わないと、不正・不整合なデータがそのままデータベースに保存されてしまう。
フロントは利便性、バックエンドは安全性の最終防衛ラインという役割分担のため両方で行うべき。

Q20. エラーハンドリング
アプリはエラーを検知して、
①ユーザーに分かりやすいエラーメッセージを表示する、
②アプリ自体がクラッシュしないようにする、
③可能であれば再試行の手段を提供する、
といった対応が必要。

第3章 データベースの基礎(8問)
==================================================

Q21. データベースとは
データベースは、大量のデータを効率的に保存・検索・更新・削除できるように整理して管理するシステム。
Excel/CSVと比べて、
①複数人・複数プログラムから同時にアクセスしても矛盾が起きないよう制御できる、
②大量データでも高速に検索できる、
③データの整合性をルールとして強制できる、
④SQLという言語で柔軟な検索・集計ができる、
といった点で優れている。

Q22. テーブル・行・列
- テーブル　　　　　Excelのシート全体
- 行（レコード）　　 シート1行
- 列（カラム）　　　 シートの一列

tasks というテーブルがあるとしたら
表全体がtasksテーブル。Excelでいうシート。

id	title	status	created_at
1	資料を作る	未完了	2026-08-21
2	メールを返信する	完了	2026-08-21
3	打ち合わせ準備	未完了	2026-08-22

1 | 資料を作る | 未完了 | 2026-08-21
この1行が、レコード。

id	
1	
2	
3
この一列がカラム


Q23. 主キー(PRIMARY KEY)
主キーは、テーブル内の各行を一意に識別するための項目。
tasksテーブルのidが主キーで、他の行と絶対に重複しない値が入る。
主キーがないと、「どのタスクを更新・削除したいか」を確実に特定できず
例えばタイトルが同じタスクが複数あった場合に区別できないため必要。

Q24. CRUD操作
CRUDはCreate(作成)・Read(読み取り)・Update(更新)・Delete(削除)の略です。
対応する機能
- Create　　POST /api/tasks(カード追加)
- Read　　　GET /api/tasks(一覧・ステータス絞り込み検索、ボード表示)
- Update　　PUT /api/tasks/{id}(編集モーダルでの保存)、PUT /api/tasks/{id}/move(並び替え)
- Delete　　DELETE /api/tasks/{id}(カード削除)

Q25. データの制約
NOT NULL　：必須項目が空のまま保存されることを防ぐため。
DEFAULT　：チェックが漏れた場合の「最後の砦」として、データベースレベルでデータの品質を保証するため。

Q26. インデックス
インデックスは、特定の列での検索を高速化するための仕組み。
本の索引に例えると、索引がなければ本を最初から最後まで1ページずつめくって
目的の単語を探す必要があるが、索引があればページ番号から直接該当箇所に飛べる。

Q27. トランザクション
トランザクションは、複数のデータベース操作を「すべて成功するか、すべて失敗して元に戻る(ロールバック)か」の
どちらかにまとめる仕組み。
カードを別カラムへドラッグ移動する処理は、移動先の列にある複数タスクのpositionをまとめて更新する。
トランザクションによって「全部更新されるか、何も更新されないか」を保証することで、データの整合性を守る。

Q28. SQLとORM
SQLはデータベースに対して「データを取得・追加・更新・削除する」ための専用の問い合わせ言語。
ORMはSQLを直接書かなくても、Javaのオブジェクトを操作するだけで、裏側で自動的にSQLを生成・実行してくれる。

第4章 開発プロセスとチーム開発(4問)
==================================================

Q29. バージョン管理(Git)
バージョン管理システムとはファイルの変更履歴を記録・管理し、過去のどの時点にも戻せるようにするシステム。
複数人が同じコードを編集しても、誰がいつ何を変更したかを追跡でき、変更を統合したり、問題があれば特定の時点に戻したりできる。
使わないと、「誰かの変更で他の人の変更が消えてしまう」「いつからこのバグが入ったのか分からない」「変更前の状態に戻せない」といった問題が起きる。


Q30. ブランチとPull Request
ブランチとは、メインの開発ライン(main)から分岐した作業用のコピーで、他の変更に影響を与えずに独立して開発を進められる。
Pull Requestの目的は、動作確認前のコードが本流に混ざって壊れたり、変更内容が可視化されずレビューできなくなることを防ぐこと。

Q31. コミットメッセージの重要性
履歴をgit logで追う際、メッセージが曖昧だと、
不具合の原因調査や変更の意図の把握に無駄な時間がかかるため。

Q32. なぜ技術的な仕組みを理解すべきか
AIはコードを書くことは得意だけど、何を作るべきか、なぜ動かないのか、どの設計が適切なのかや
クライアントの真の要望、汲み取る力の部分は人間にしかできず、仕組みを理解していないと、
設計が上手くできないので、技術的な仕組みは理解しておくべきだと思います。
